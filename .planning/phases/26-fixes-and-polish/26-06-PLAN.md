<objective>
POL-06, server half: give `/api/generate` and `/api/edit-post` the same idempotency contract carousel and enhancement have shipped with since v1.1.

Purpose: these are the last two generation-adjacent routes without duplicate-request protection. A double-submit or a client retry after a completed-but-unacknowledged response currently creates a second post (or a second version) and charges the user twice. 26-CONTEXT.md locks the design as an exact mirror of the existing contract — including its known true-race behavior, which this plan replicates rather than improves.
Output: two Zod fields, one additive migration, two pre-flight SELECTs placed before the credit gate, and two insert fields.
</objective>

The shipped pattern (`server/routes/carousel.routes.ts:340-354`, identical in `server/routes/enhance.routes.ts:204-219`):
```typescript
const adminSb = createAdminSupabase();
const { data: existingPost } = await adminSb
    .from("posts")
    .select("*")
    .eq("idempotency_key", parsed.idempotency_key)
    .eq("user_id", user.id)
    .maybeSingle();
if (existingPost) {
    return res.status(200).json({ idempotent: true, post: existingPost });
}
```
Placement in both: AFTER Zod validation and key/brand resolution, BEFORE the credit gate. That ordering is the point — a resubmit must never re-run `checkCredits`.

The shipped migration shape (`supabase/migrations/20260421000000_v1_1_schema_foundation.sql:29-38`):
```sql
alter table public.posts add column if not exists idempotency_key text;
create unique index if not exists posts_idempotency_key_unique
  on public.posts (idempotency_key) where idempotency_key is not null;
```

CRITICAL (26-RESEARCH.md Pitfall 3): `post_versions` has NO `user_id` column — ownership is enforced by an RLS policy that joins to `posts.user_id` (`supabase/migrations/20260304000002_add_post_versions_table.sql`). `.eq("user_id", user.id)` on that table is a runtime "column does not exist" error against the admin client. Scope the edit-side dedup by `(idempotency_key, post_id)`. That is equally safe: `edit.routes.ts:268-278` already fetched the post with `.eq("id", post_id).eq("user_id", user.id)` and returned 404 otherwise, so by the time the pre-flight runs, `post_id` is proven to belong to the caller.

CRITICAL (26-RESEARCH.md Pitfall 4, and 26-CONTEXT.md's locked decision): the existing contract does NOT gracefully handle a TRUE concurrent race — both requests pass the pre-flight, the loser's insert violates the unique index and surfaces as a generic 500. `carousel-generation.service.ts:868-873` documents this in its own comment. Replicate it. Do NOT add unique-violation catch-and-return-200 handling; that is a deliberate scope expansion CONTEXT.md did not ask for.

Both routes are SSE. The pre-flight MUST return plain JSON before the SSE stream is initialized — exactly like `carousel.routes.ts` does. In `generate.routes.ts` the SSE stream opens at the "── Initialize SSE stream ──" comment; everything before it still returns JSON.
