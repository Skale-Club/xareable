# Phase 21.1: Affiliate BYOK Migration - Context

**Gathered:** 2026-07-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Admin/affiliate bring-your-own-key accounts migrate from Gemini/OpenAI keys to OpenRouter keys — provisioning and rotation work end-to-end, and every generation made with an affiliate's key is billed to that affiliate's OpenRouter account, never the platform balance. Old key columns are retained dead (additive migration, no lockout).

</domain>

<decisions>
## Implementation Decisions

### Key Resolution & Rollback Behavior
- `getOpenRouterApiKey(profile)` mirrors `getGeminiApiKey`/`getOpenAIApiKey` exactly: affiliate-only BYOK tier (`usesOwnApiKey(profile)` gate), no silent fallback to a platform-default OpenRouter key for affiliates.
- Admin continues to use the platform's OpenRouter key — `usesOwnApiKey` only returns true for `is_affiliate`, unchanged from the existing pattern; admins are NOT required to configure their own key.
- Missing-key error is the exact established string: `"Affiliate accounts must configure their own OpenRouter API key in Settings before generating."` — returned as a structured `{ key: "", error }` result, never a silent 401 mid-SSE-stream.
- No fallback to the direct Gemini path when an affiliate lacks an OpenRouter key — the error is explicit and blocks generation up front (consistent with SC3).

### Migration & Backward Compatibility
- New column: `profiles.openrouter_api_key` (additive migration, nullable, no columns dropped).
- `api_key` / `openai_api_key` columns remain in the schema, retained dead (no longer read by the new gateway key-resolution path) — zero risk of affiliate lockout mid-migration.
- No automatic migration/copy of old key values into the new column — different provider/account, affiliate must reconfigure manually via Settings.
- Billing uses provider pinning: the OpenRouter key resolved for a request is used for that entire request/generation; no mid-request key switching. Verified via a simulated-failure test per SC2.

### Settings UI
- Reuse the exact visual/state pattern of the existing `openai_api_key` field in `client/src/pages/settings.tsx` (same component shape, same save flow via direct Supabase `profiles` update).
- Field is visible only when `profile.is_affiliate === true` — same condition used by `usesOwnApiKey`.
- No client-side key-format validation — validated server-side on first real gateway call, same as the existing Gemini/OpenAI key fields.
- The old Gemini/OpenAI key input fields are removed from the affiliate-facing Settings UI, replaced by the single OpenRouter key field (they remain functional as dead code server-side per the migration decision above, but are no longer surfaced to affiliates in the UI).

### Claude's Discretion
- Exact DB migration file naming/timestamp, exact admin-panel wording beyond the specified error string, and internal helper function structure are left to implementation.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `server/middleware/auth.middleware.ts`: `usesOwnApiKey()`, `getGeminiApiKey()`, `getOpenAIApiKey()`, `getPlatformDefaultApiKey()` — exact pattern to mirror for `getOpenRouterApiKey()`.
- `client/src/pages/settings.tsx`: existing `geminiApiKey`/`openaiApiKey` state + save handlers (lines ~78-81, ~356, ~373) — pattern to replicate for `openrouterApiKey`.
- Phase 21's `server/services/ai-gateway.service.ts` (`chatCompletion`, `transcribe`, `generateImage`, `editImage`) — all currently take the platform's `OPENROUTER_API_KEY`; this phase makes the key parameter affiliate-aware.

### Established Patterns
- 3-tier key resolution: affiliate → own profile column; admin/regular/business → shared `platform_settings` key (managed via `/admin` → Platform API Keys).
- Additive-migration convention used throughout the project (e.g., Phase 18 brand references, Phase 21's `usage_events.metadata`) — never drop/rename columns in active use.
- `recordUsageEvent`/`quota.ts` already has per-user billing plumbing (Phase 21 added real-cost fields) — affiliate billing must route the request's actual OpenRouter cost to the affiliate's own account context, not the platform's.

### Integration Points
- Every gateway call site from Phase 21 (`gemini.service.ts`, `carousel-generation.service.ts`, `caption-quality.service.ts`, `enhancement.service.ts`, `transcribe.routes.ts`, `image-provider.ts`'s `OpenRouterImageProvider`) currently resolves a single platform `OPENROUTER_API_KEY` — this phase must thread the affiliate's own key through those same call sites when `profile.is_affiliate === true`.
- `client/src/pages/settings.tsx` affiliate-conditional key fields.

</code_context>
