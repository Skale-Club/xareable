## Summary

Phase 21 built the OpenRouter gateway itself and left one explicit gap, called out in its own code comments: `OpenRouterImageProvider` and all five text/transcription call sites resolve `config.OPENROUTER_API_KEY` (the **platform's** key) unconditionally, deliberately ignoring the `apiKey`/`input.apiKey` parameter that route handlers already populate with a per-user resolved key. The comment at `image-provider.ts:265-267` says this explicitly: *"Uses the PLATFORM OpenRouter key... ignoring input.apiKey... Affiliate BYO OpenRouter keys land in Phase 21.1."* This means that **today, every affiliate's generation is actually billed to the platform's own OpenRouter account**, even though the app's internal credit ledger correctly never charges affiliates internally (`!ownApiKey` guards on `checkCredits`/`deductCredits` already exist in all 5 affected routes). This is the real cost leak GATE-06 closes — it is not a net-new billing feature, it is finishing a wire that Phase 21 intentionally left dangling.

Because each affiliate's OpenRouter key belongs to a **completely separate OpenRouter account** (their own signup, their own credit balance — not OpenRouter's own "Management API keys" or "BYOK" product features, see the terminology note below), cost isolation is achieved by construction the moment the correct key is threaded end-to-end for a given request: OpenRouter's own metering always deducts from whichever account owns the `Authorization: Bearer <key>` used for that HTTP call, regardless of which underlying model provider OpenRouter internally routes to. **No new server-side billing math is needed** — the existing `!ownApiKey` skip on `deductCredits` is already correct; the only gap is which literal key string reaches the `fetch`/OpenAI-SDK call.

The one genuinely hard architectural problem this phase must solve is **not** billing math — it's that the EXISTING eager, unconditional `getGeminiApiKey(profile)` gate at the top of every one of the 5 SSE routes (`generate`, `edit`, `carousel` ×2, `enhance`) plus `transcribe` would, once the Gemini key input field is removed from the affiliate Settings UI (a locked decision), permanently lock out every *new* affiliate who never had a chance to set `profile.api_key`. This must be restructured so the Gemini-key gate applies only to non-affiliates, and a new OpenRouter-key gate applies to affiliates instead — see Pitfall 1, this is the load-bearing finding of this research.

**Primary recommendation:** Add `getOpenRouterApiKey(profile)` to `auth.middleware.ts` (identical shape to `getGeminiApiKey`, but sourcing the "platform default" branch from `config.OPENROUTER_API_KEY` — an env var, per Phase 21's precedent — not a new `platform_settings` row). At each of the 6 call sites, thread a new optional key parameter (`openRouterApiKey`) alongside the existing `apiKey`/`imageApiKey` parameters — this exactly repeats the established `imageApiKey?: string; // overrides apiKey for image calls when provider != gemini` pattern already used for the OpenAI image provider. Replace every hardcoded `config.OPENROUTER_API_KEY` read inside the six call sites' `routing === "openrouter"` branches with `params.openRouterApiKey || config.OPENROUTER_API_KEY`. At the route level, branch the *initial* key-gate on `usesOwnApiKey(profile)`: affiliates resolve+gate on `getOpenRouterApiKey`, everyone else keeps the existing `getGeminiApiKey` gate unchanged.

## Terminology Trap: OpenRouter's own "BYOK" feature vs. this phase's "affiliate OpenRouter key"

**This is a real documentation-collision risk — flagging explicitly so the planner doesn't accidentally build the wrong feature.**

OpenRouter has an official product feature also called "BYOK" (`openrouter.ai/docs/use-cases/byok`): a *single* OpenRouter account owner attaches their own upstream provider credentials (their own OpenAI/Anthropic/Google Vertex account) to OpenRouter account settings, so OpenRouter proxies requests using the customer's provider credits instead of OpenRouter's pooled ones — the request is still authenticated with an **OpenRouter** API key and still billed to the **same OpenRouter account** (with a small BYOK service fee, historically ~5%).

**That is NOT what this phase does.** Phase 21.1's "Affiliate BYOK Migration" means: each affiliate signs up for their **own, separate OpenRouter account** (their own dashboard, their own credit balance) and pastes **that account's own API key** into `profiles.openrouter_api_key` — exactly the same pattern already used for `api_key` (Gemini) and `openai_api_key` today. This is ordinary multi-tenant key resolution, not OpenRouter's BYOK provider-credential feature. Do not build anything against OpenRouter's Provisioning/Management API (`openrouter.ai/docs/features/provisioning-api-keys`) for this phase — that API is for programmatically minting sub-keys *within* one parent account with shared-pool spend limits, which is a different model than what's needed here (verified via WebSearch: *"All your keys draw from the same account credit balance... the per-key limit caps how much each individual key can spend"* — that describes sibling keys under ONE account, not the fully独立 separate-account model this phase requires).

## Architecture Patterns

### Pattern 1: New `getOpenRouterApiKey` helper — exact mirror of `getGeminiApiKey`, with one deliberate divergence

Add to `server/middleware/auth.middleware.ts` (after `getOpenAIApiKey`, line 297):

```typescript
/**
 * Resolve the OpenRouter API key for a user (Phase 21.1 — GATE-06).
 * - Affiliate: their own profiles.openrouter_api_key (own OpenRouter account,
 *   own credit balance — a DIFFERENT account than the platform's, not
 *   OpenRouter's own "BYOK" provider-credential feature).
 * - Admin / regular / business: the platform's OPENROUTER_API_KEY env var
 *   (NOT platform_settings — Phase 21 deliberately made this an env var,
 *   unlike gemini_api_key/openai_api_key which ARE platform_settings rows;
 *   do not introduce a second source of truth for the platform OpenRouter key).
 */
export async function getOpenRouterApiKey(
    profile: { openrouter_api_key?: string | null; is_admin?: boolean; is_affiliate?: boolean } | null
): Promise<{ key: string; error?: string }> {
    const ownKey = usesOwnApiKey(profile);

    if (ownKey) {
        if (!profile?.openrouter_api_key) {
            return {
                key: "",
                error: "Affiliate accounts must configure their own OpenRouter API key in Settings before generating.",
            };
        }
        return { key: profile.openrouter_api_key };
    }

    const { config } = await import("../config/index.js");
    if (!config.OPENROUTER_API_KEY) {
        return {
            key: "",
            error: "OpenRouter API key not configured. Ask the platform admin to set OPENROUTER_API_KEY.",
        };
    }
    return { key: config.OPENROUTER_API_KEY };
}
```

**Why the divergence is correct, not a mistake:** `getGeminiApiKey`'s non-owner branch calls `getPlatformDefaultApiKey("gemini_api_key")`, which reads a `platform_settings` row (admin-editable via `/admin` → Platform API Keys, no redeploy needed). Phase 21 explicitly chose `OPENROUTER_API_KEY` as a **Zod-validated env var** in `server/config/index.ts:36` (`OPENROUTER_API_KEY: z.string().min(1).optional()`), not a `platform_settings` row — every one of the 6 existing call sites already reads `config.OPENROUTER_API_KEY` for the platform tier. If `getOpenRouterApiKey`'s non-owner branch instead added a NEW `platform_settings` row, the codebase would end up with two disconnected sources of truth for "the platform's OpenRouter key" (one env var, one DB row) with no code ever reading the DB one — a bug waiting to happen. **Literal mirroring only applies to the affiliate-tier branch** (the part CONTEXT.md's decisions actually describe in detail); the platform-tier branch should reuse Phase 21's already-established `config.OPENROUTER_API_KEY`.

### Pattern 2: The route-level key gate MUST branch by `usesOwnApiKey`, not run both checks unconditionally

**This is the single most important structural change in this phase — get it wrong and every new affiliate is locked out (violates ROADMAP SC1: "no affiliate is locked out mid-migration").**

Today, every one of the 5 SSE routes (`generate.routes.ts:224`, `edit.routes.ts:167`, `carousel.routes.ts:146` and `:659`, `enhance.routes.ts:132`) and `transcribe.routes.ts:95-110` calls `getGeminiApiKey(profile)` **unconditionally** at the top of the handler and hard-blocks (`return res.status(400).json({message: keyError})`) if it errors — this happens *before* `getCallRouting()` is ever consulted, and *before* any provider-specific branching. Once this phase removes the Gemini API key input field from the affiliate-facing Settings UI (a locked decision), a brand-new affiliate has **no way to ever populate `profile.api_key`** — meaning the existing unconditional gate would return its established Gemini-key error for every single one of their requests, forever, regardless of `ai_gateway_routing` being `"openrouter"` (the default, which never even touches `profile.api_key`).

The fix: branch the initial gate on `usesOwnApiKey(profile)` (already computed in every route as `ownApiKey`):

```typescript
// Replace the unconditional getGeminiApiKey(profile) call+gate with:
const ownApiKey = usesOwnApiKey(profile);
let geminiApiKey = "";
let openRouterApiKey = "";

if (ownApiKey) {
    const { key, error } = await getOpenRouterApiKey(profile);
    if (error) {
        await logGenerationError({ userId: user.id, errorMessage: error, errorType: "configuration", requestParams: sanitizedRequestParams });
        return res.status(400).json({ message: error });
    }
    openRouterApiKey = key;
    // geminiApiKey intentionally left "" for affiliates — only matters if an
    // admin flips ai_gateway_routing to "direct" mid-incident; see Pitfall 2.
} else {
    const { key, error } = await getGeminiApiKey(profile); // unchanged, platform-tier
    if (error) {
        await logGenerationError({ userId: user.id, errorMessage: error, errorType: "configuration", requestParams: sanitizedRequestParams });
        return res.status(400).json({ message: error });
    }
    geminiApiKey = key;
}
```

This preserves the exact existing pre-SSE, structured-JSON-400 error shape (matches CONTEXT.md: *"never a silent 401 mid-SSE-stream"* — the check now happens even earlier than today, before SSE init, for affiliates) and satisfies SC1 (no lockout) simultaneously.

`transcribe.routes.ts` needs the analogous change: its `ownApiKey && !transcribeProfile?.api_key` check (line 59) and the `if (ownApiKey) { ... geminiApiKey = transcribeProfile.api_key; }` block (lines 96-101) both need to become OpenRouter-key checks for affiliates (this route's `SELECT` at line 40 also needs `openrouter_api_key` added to the column list).

## Common Pitfalls

### Pitfall 1: The existing unconditional Gemini-key gate will lock out every new affiliate if not restructured (HIGH severity, HIGH confidence)

**What goes wrong:** Every one of the 5 SSE routes plus `transcribe.routes.ts` calls `getGeminiApiKey(profile)` unconditionally at the top of the handler today and hard-blocks on error, *before* any routing/provider branching happens. Once the Gemini key input field is removed from the affiliate Settings UI (a locked decision of this phase), a new affiliate has no way to ever set `profile.api_key`, so this pre-existing gate returns its established error ("Affiliate accounts must configure their own Gemini API key...") for literally every request, forever — even though `ai_gateway_routing` defaults to `"openrouter"` and never touches `profile.api_key` at all in that case.

**Why it happens:** This gate predates the gateway entirely (Phase 12.3) and was never revisited when Phase 21 added OpenRouter routing underneath it — Phase 21's own scope explicitly deferred "affiliate BYOK" to this phase, so the gate was left as-is by design, not by oversight.

**How to avoid:** Restructure the gate per Architecture Pattern 2 above — branch on `usesOwnApiKey(profile)` and route affiliates to the new `getOpenRouterApiKey` check instead of `getGeminiApiKey`. This is not optional polish; it is required to satisfy ROADMAP SC1 ("no affiliate is locked out mid-migration").

**Warning signs during implementation:** if a static verify script only checks "does `getOpenRouterApiKey` exist and get called somewhere," it will pass even if the old unconditional gate is left completely untouched. The verify script for this phase MUST assert that the **old** `getGeminiApiKey` call site is now conditional (e.g., regex for `if (ownApiKey)` / `if (!ownApiKey)` bracketing both key-resolution calls in each of the 6 files), not just that a new function was added.

### Pitfall 2: The rollback (`ai_gateway_routing = "direct"`) edge case for affiliates is a known, accepted gap — do not over-engineer a fix

**What goes wrong (if attempted, not if left alone):** If Pattern 2 leaves `geminiApiKey = ""` for affiliates (since they no longer have a way to set it via UI), and an admin later flips `ai_gateway_routing.planning` (or `.image`/`.transcription`) to `"direct"` as a GATE-07 emergency rollback, `gemini.service.ts:661`'s `if (routing === "direct" && !this.apiKey) { throw new Error("Gemini API key not configured"); }` will throw for every affiliate. That thrown error is caught by `generate.routes.ts`'s outer `catch (textError)` block (line ~446), which **silently degrades to `buildTextFallback(...)`** (a generic template) rather than surfacing a clear error — this is a worse UX than SC3's "clear blocking error," but it is a genuinely rare, admin-triggered, temporary state (GATE-07's whole design intent is "emergency, short-lived, not a steady-state configuration").

**Why it happens:** The retained-dead `profile.api_key` column has no UI path to populate for NEW affiliates once this phase ships, but the direct/legacy rollback code path still depends on it being present.

**How to avoid:** Do not attempt to build a new UI path, migration, or fallback specifically to keep affiliates working on the "direct" rollback path — this is explicitly out of CONTEXT.md's locked scope. Simply document the limitation (e.g., a code comment at the `if (routing === "direct" && !this.apiKey)` check, or a note in the admin panel near the `ai_gateway_routing` toggle) so a future operator flipping this switch during an incident understands affiliates may need manual `profile.api_key` backfill via direct DB access if the rollback needs to persist for an extended period with active affiliate traffic. Flagging, not fixing, is the correct scope here.

### Pitfall 3: Fixing `image-provider.ts` alone without the matching route-level branch silently re-introduces the bug

**What goes wrong:** If only `OpenRouterImageProvider.generate()`/`.edit()` are changed to prefer `input.apiKey`, but the 4 routes' `let imageApiKey = geminiApiKey; if (provider.name === "openai") {...}` blocks are left untouched, then for `provider.name === "openrouter"` (the default), `imageApiKey` stays equal to `geminiApiKey` — which is `""` for affiliates per Pattern 2. An empty string is falsy, so `input.apiKey || requireOpenRouterKey()` would fall through to the platform key anyway — **the exact bug this phase exists to fix, silently reintroduced** for the image leg specifically, while the text/planning leg appears fixed. This is the kind of gap that passes a naive "does `OpenRouterImageProvider` read `input.apiKey`" static check while still failing the actual behavioral requirement (SC2).

**How to avoid:** Both halves of Pattern 3's image-path fix (the `image-provider.ts` change AND the new `else if (provider.name === "openrouter")` branch in all 4 routes) must land together and be verified together — e.g., a functional check that constructs a fixture affiliate profile, calls the route-level key-resolution logic, and asserts the value passed to `provider.generate({apiKey: ...})` equals the affiliate's `openrouter_api_key`, not the platform key.

### Pitfall 4: Module-level single-slot OpenRouter client cache thrashes once multiple distinct keys are in flight (LOW severity, performance-only, HIGH confidence — grounded in code read)

**What goes wrong:** `ai-gateway.service.ts:39-49` caches exactly one `{key, client}` pair at module scope:
```typescript
let cachedClient: { key: string; client: OpenAI } | null = null;
function getOpenRouterClient(apiKey: string): OpenAI {
  if (cachedClient && cachedClient.key === apiKey) return cachedClient.client;
  const client = new OpenAI({ apiKey, baseURL: OPENROUTER_BASE_URL, defaultHeaders: OPENROUTER_ATTRIBUTION_HEADERS });
  cachedClient = { key: apiKey, client };
  return client;
}
```
This is **not a correctness/security bug** — the function body is fully synchronous (no `await` between the check and the write), so Node's single-threaded event loop guarantees no cross-request key leakage; a call with a different key always constructs (and correctly uses) a fresh client. But once affiliate traffic starts interleaving with platform-key traffic (which will happen immediately once this phase ships, since admin/regular/business users share the platform key while affiliates use their own), this single-slot cache provides **zero** caching benefit in practice — it constantly evicts and reconstructs on every request whose key differs from the previous request's key, regardless of concurrency level.

**How to avoid:** Not a required fix for GATE-06 (no behavioral requirement depends on this cache being effective — `OpenAI` client construction is cheap, no network call at construction time). Flag as an optional follow-up: upgrade `cachedClient` to a small `Map<string, OpenAI>` (or an LRU) if profiling ever shows this matters. Do not silently "fix" this as an unplanned scope addition unless the plan explicitly calls it out — it's a pre-existing Phase 21 artifact, not something GATE-06 introduces.

### Pitfall 5: Per-call-class routing means "does this affiliate need an OpenRouter key" isn't determined by a single flag

**What goes wrong:** `ai_gateway_routing` has three independent admin toggles (`planning`, `image`, `transcription`) — an admin could in theory set `image: "direct"` while leaving `planning`/`transcription` on `"openrouter"`. The eager, unconditional gate recommended in Pattern 2 (block if affiliate has no OpenRouter key, regardless of current routing) means an affiliate would be blocked even in a hypothetical world where every call class they'd actually hit happens to be routed `"direct"` for them.

**How to avoid:** This is an accepted, intentional simplification, not a bug — CONTEXT.md's locked wording ("blocks generation up front") matches exactly how `getGeminiApiKey` already behaves today (also checked unconditionally, ignoring which image provider will end up being used). Do not build a per-call-class-aware gate that queries `getCallRouting()` three times at the route top just to conditionally skip the OpenRouter-key check — that adds real complexity for an edge case (all three routing toggles flipped to `"direct"` simultaneously while affiliates are active) that GATE-07's rollback is not designed to sustain long-term anyway.

## Open Questions

1. **Should `provider.only`/`provider.order`/`allow_fallbacks: false` ever be added to the affiliate-key OpenRouter calls, given the phase's success-criteria wording mentions "provider pinning"?**
   - What we know: OpenRouter's account-level billing is determined solely by which API key authenticates the request, independent of which upstream model provider OpenRouter internally selects to fulfill it (confirmed via `openrouter.ai/docs/guides/routing/provider-selection`, live-fetched this pass). This codebase's OWN `callWithFallback` (model-slug-level fallback, e.g. `gemini-2.5-flash` → a configured fallback slug) already keeps the SAME resolved `apiKey` constant across every attempt in the loop (`ai-gateway.service.ts:82-110` builds one `OpenAI` client from `params.apiKey` before entering the loop) — so cost pinning already holds across both OpenRouter's own internal provider routing AND this codebase's model-slug fallback, with zero additional code.
   - What's unclear: whether "verified with provider pinning on a simulated failure" (ROADMAP SC2's exact wording) refers to an actual `provider.only`/`allow_fallbacks` HTTP param that should be ADDED to the request, or simply describes the **verification technique** (force a failure — e.g., point `model` at a deprecated/invalid slug for the affiliate's key — and confirm the whole call fails/falls-back cleanly still attributed to the affiliate's account, with no leak to the platform key).
   - Recommendation: read SC2 as a verification technique, not a new request parameter, given the Don't-Hand-Roll finding above (billing isolation needs no extra HTTP params). If a manual/functional verification step is written for SC2, it should: (a) resolve an affiliate's OpenRouter key, (b) deliberately request a nonexistent/deprecated model slug (or a slug not covered by that key's account balance/spend limit) so the call fails, (c) assert the resulting error surfaces cleanly (per Pitfall 3's shape) and that no `deductCredits`/platform-balance charge occurred — this satisfies "verified with provider pinning on a simulated failure" without adding new `provider.*` request fields.
